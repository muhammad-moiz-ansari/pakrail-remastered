# Implementation and simulation notes

Next.js App Router + React + strict TypeScript, CSS, Lucide icons and native SVG. No production accounts, database, maps or payment SDK. The vertical slice is the entire guest booking task, including recovery; broader railway services are deferred. The repository root is the supplied implementation location.

The domain functions in `src/lib/booking.ts` own fixtures, pricing, validation, passenger transitions, class/train invalidation, seat assignment and recommendation. `search-form.tsx` owns guided search/popovers; `booking-app.tsx` coordinates the route-specific UI. Fixtures and domain rules can be replaced without importing a service into the visual components. `sessionStorage` holds a versioned fictional draft after hydration. No contact or traveller names enter URLs. State guards recover direct entry to the earliest missing step. Invalid/old storage recovers with a message and fresh draft. Storage is per tab; this is not cross-device persistence or a seat hold.

Dates are date-only strings; today comes from Asia/Karachi. Timetable instants use explicit `+05:00`, and return filtering compares against outbound arrival, including overnight. Four fictional services work between six station choices; Karachi legs take 17h, other legs 4h30m. Today excludes departed trains. Capacity, amenities and geometry are intentionally illustrative.

Pricing uses integer rupees. Each adult/child occupies one seat and pays that leg’s class fare. Economy multiplier 1, AC Standard 1.6, Business 2.2; round per-passenger class fare to an integer. Business has capacity four; other classes support the demo group limit. Sum each leg × traveller count. Seat selection adds zero. DEMO10 subtracts 10% of the summed base, rounded once. Invalid vouchers do not block full-price booking; removing a voucher restores the base.

Provisional recommendation: deterministic coach A/B inventory; try enough sequential free seats in one four-seat row; otherwise use stable coach/seat order. Exclude sold, conflicted and assigned seats. Run on initial unassigned seats, preserve manual choices, and track suggestions separately. Dialog cancellation leaves the old seat. Confirmation atomically replaces the active passenger’s assignment. Assignments are keyed by leg and stable passenger ID. Removal releases both legs; class/train changes release only that leg. Search explicitly renews train/seat selections while retaining matching traveller cards and contact details. This is not a production allocation algorithm.

Use `/demo` outside the traveller flow. Select Normal to restore ordinary fixtures; No results to force empty results (Clear filters and retry restores Normal); Search error to show failure (Retry search restores Normal); Seat conflict to release the first passenger’s actual outbound seat on the next Review attempt and mark it unavailable (select replacement); Payment failure to fail the next Pay attempt once (Retry succeeds). Reset uses a confirmation. Scenario controls never request real payment credentials.

Open decisions / limitations: IA awaits card sort; rank 0–3 omitted (R3 limitation); no unverified age bands, concessions or gender-based seat meanings. Sold seats are neutral while pink/blue meanings are unresolved. Real map/data, animation, production algorithm, real inventory, accounts, issuance and a ten-minute hold timer remain deferred. The prototype has no verified hold or expiry promise. Academic readiness depends on human evidence and checkpoint, not coding alone.
