# Phase 6: integrated verification (3-4 November 2026, Asia/Karachi)

The local integration audit is complete. A genuine Safepay sandbox **session** was created; authenticated provider capture through to a ticket is **not verified**. No card was submitted, no money was charged, and no provider-paid booking was created. Checkout remains disabled in normal local configuration. The saved temporary public webhook hostname no longer resolved when checked, so an authentic payment callback could not be verified end-to-end. Previous dashboard delivery tests remain historical evidence of signature acceptance, not evidence of a completed card transaction.

## Fixes discovered during verification

- `src/components/ticket-print.tsx`: a valid completed booking returned HTTP 500 on a direct owner ticket page request. The client component also renders on the server, where `document` does not exist. Its body portal now uses a null server snapshot and attaches only after hydration. The actual owned route subsequently returned 200; guests and other accounts remained blocked. The print renderer also asserts that server rendering a valid ticket component no longer accesses the DOM.
- `src/components/booking-app.tsx`: the review busy message now says the journey and selected places are being checked. The actual checkout step says it is opening Safepay sandbox checkout. Neither claims a payment is processing before login or gateway handoff.
- `scripts/check-accounts.ts`: added payment-session guest rejection and a valid, explicitly tagged local ticket/status fixture for cross-account HTTP verification. `scripts/check-phase6.ts`, `scripts/phase6-http-probes.ts`, and `scripts/phase6-print.tsx` cover isolated payment-state checks, guest/webhook/map endpoints, and reproducible ticket output.

## Reproduction and project checks

- `npm test`: 110 passed. TypeScript, ESLint, Prettier, `git diff --check` and production `npm run build` (including local MapLibre worker preparation) passed. Build process alone disabled Mongo configuration; real runtime credentials were unchanged.
- `npm run accounts:check`: requires local development server on the exact configured Better Auth origin; creates fresh tagged/local QA records. No existing user, historical ticket, or production catalogue data was edited.
- `npx tsx scripts/check-phase6.ts --run`: creates a separate QA database for synthetic signed confirmations, blocks unexpected provider requests and writes ignored `.local/phase6/ticket-fixture.json`. Does not change the main database.
- `npx tsx scripts/check-phase6.ts --run --provider`: genuine sandbox session creation only, separate QA database, no card submission. Do not treat the QA tracker as a completed booking.
- `npx tsx scripts/phase6-http-probes.ts --run`: local HTTP guest/webhook/map checks; records a labelled unknown-tracker receipt only, no booking.
- `npx tsx scripts/phase6-print.tsx`: renders `.local/phase6/ticket.html` (native print button) and `.local/phase6/ticket-screen.html` (standalone screen emulation) using the actual template, CSS and local logo. Both are synthetic QA artifacts and gitignored.
- Existing dummy-instrument seed: `node --import tsx scripts/payment-fixtures.ts --development-database` with PAYMENT_MODE=sandbox, development-only enforcement and the Safepay API reference as source. The Phase 6 checks did not submit any instrument. See https://safepay.helpscoutdocs.com/article/82-testing-the-latest-safepay-checkout-integration for provider test procedure.
